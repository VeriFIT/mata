Mata: The Automata Library

Mata is an open source automata library that offers interface for different kinds of automata, e.g. (non-)deterministic finite automata (NFAs), (non-)deterministic finite transducers, etc. Currently, Mata offers three interfaces:

  1. An efficient library implemented in C/C++,
  2. A flexible wrapper implemented in Python that uses the efficient library, and
  3. Rust bindings with a safe API over the efficient library.

The website of Mata gives an overview of the library, its documentation (C++, Python, Rust), and a playground that runs Mata in the browser. The development website tracks the devel branch.

Installation

Nix

Available in nixpkgs (maintained by @Adda0) as pkgs.mata:

nix build nixpkgs#mata

This repo also provides a flake (maintained by @Adda0) with flake-compat and an overlay:

nix build github:VeriFIT/mata

The flake also packages the Rust bindings with their examples (mataRust) and the mata command-line interface (mataCli):

nix build github:VeriFIT/mata#mataRust
nix run github:VeriFIT/mata#mataCli -- --help

For development:

nix develop github:VeriFIT/mata

The development shell includes Cargo, rustc, Clippy, and rustfmt from a lockfile-pinned stable Rust toolchain. The Python environment of the development shell is built from uv.lock, the same versions uv sync installs, with the bindings installed editable from the checkout. Build their extensions in place with just bindings python build.

Download pre-built binaries from GitHub

You can download pre-built binaries from the releases page on GitHub.

Building and installing from sources

For a successful installation of Mata, cmake of version 3.23.0 (or higher) and a C++ compiler with a support of C++-20 standard is required. From optional requirements, doxygen is required for a generation of the documentation and catch2 is required for the unit testing (Mata can still be compiled without these optional dependencies).

The Mata library further depends on the following libraries, included in the ./3rdparty/ directory:

  • cudd for BDD manipulation,
  • re2 for regular expression parsing and the corresponding automata construction, and
  • simlib for a simulation computation.

The experimental reduction of automata to automata with the minimum number of states (reduce() with the "sat" or "qbf" algorithm) runs an external SAT or QBF solver. Mata finds the solver in PATH (CaDiCaL, Kissat, CryptoMiniSat, or PicoSAT; DepQBF or CAQE), or uses the command in the environment variable MATA_SAT_SOLVER or MATA_QBF_SOLVER. For example, run apt install cadical depqbf or brew install cadical depqbf. The solvers are needed only for this reduction, not for building or using the rest of Mata.

To build the library, run the following:

git clone https://github.com/VeriFIT/mata
cd mata
make release

For C++ executables, install mimalloc and build with MATA_USE_MIMALLOC=ON:

make release MATA_USE_MIMALLOC=ON

The option is off by default and cmake fails if mimalloc cannot be found. The Nix C++ package enables it. The allocator applies to the final executable, so consumers linking libmata.a without the exported CMake target must also link mimalloc themselves. A measurement over Mata operations on the automata-lib-bench TACAS'24 experiments and selected NFT programs reduced total runtime by 26.6%; the effect varies by workload.

Independently of the global allocator, Mata chooses how it allocates the heap blocks of Delta (the transitions of automata), with MATA_DELTA_ALLOCATOR:

  • std (the default) takes them from the global operator new/delete, i.e., whatever allocator the executable uses.
  • pool carves them from thread-local 1 MiB chunks in allocation order, so a Delta built state by state lies in consecutive memory. It is faster on composition-heavy workloads. The chunks are reused, but never returned to the operating system before the process exits.

Select it per process with the environment variable, without rebuilding:

MATA_DELTA_ALLOCATOR=pool ./my-program

The variable is read on the first allocation and fixed for the rest of the process; an unknown value throws std::invalid_argument. The CMake option of the same name sets the default used when the variable is unset: make release MATA_DELTA_ALLOCATOR=pool.

mimalloc, in contrast, replaces the allocator of the whole process, so it is chosen when the executable is linked (MATA_USE_MIMALLOC=ON) or started (LD_PRELOAD=/path/to/libmimalloc.so ./my-program), never while it runs. The two combine freely. When the memory runs out, the system allocator makes Mata throw std::bad_alloc, while mimalloc may abort the process instead.

In order to install the library, you can run

sudo make install

In order to verify the functionality of the library, you can run the test suite:

make test

You might, need to install the dependencies to measure the coverage of the tests. Run the following to install the dependencies for macOS:

brew install lcov gcovr

Run the following to install the dependencies for Ubuntu:

sudo apt install -y build-essential lcov gcovr xdg-utils

Python binding

Mata offers binding of its efficient library to Python. You can install the binding as a Python package on your system as follows.

Installation from PyPI

To install the latest version from the PyPI repository, run:

# Using uv: {#using-uv}
uv add libmata
# Or using pip: {#or-using-pip}
pip3 install libmata

Building from sources (Python)

To build from sources first, install the necessary requirements for Python and your system. We recommend using the virtual environemnt (venv) to install and use the library.

Using uv:

uv sync --python 3.13

Besides the dependencies of the bindings, uv sync installs the dev dependency group: the tools to build the bindings in place, the packages the tests and the notebooks import, and the tools to sync the notebooks and to render the documentation.

Or using pip:

python3 -m pip install --upgrade pip
make -C bindings/python init
sudo apt -qq update
sudo apt -qq install -y graphviz graphviz-dev

make init installs the bindings with the dev, pandas and plotting extras: Cython, setuptools and CMake for the in-place build, pytest, and the packages the tests import. pip install libmata alone installs no runtime dependencies; building it from the sdist when no wheel fits still pulls its build dependencies into an isolated environment.

Now, you can install the library.

make -C bindings/python install

Finally, you can verify the binding woks as expected by running the test suite:

make -C bindings/python test

Rust binding

Mata offers bindings of its library to Rust in bindings/rust: the crate mata with a safe API, and the crate mata-sys, which builds the library. They need Rust 1.95 or newer besides the requirements of the library. The module mata::lazy (the crate mata-lazy) checks combinations of NFAs and NFTs for emptiness lazily, and the module mata::logic (the crate mata-logic) decides formulas encoded in automata on top of it. The same workspace builds the mata command, the command-line interpreter of Mata Script; see bindings/rust/README.md.

Installation from crates.io

To add the latest version to a Cargo project, run:

cargo add mata

Building from sources (Rust)

To build the bindings and run their tests:

cd bindings/rust
cargo test --workspace --all-features

Getting started

To get started, we refer to the folder examples in our repository. This directory contains examples of various usage in form of:

  1. C/C++ example programs. By default, they are built with the library. To run for example the first example:
./build/examples/example01-simple
  1. Python example scripts. To run the scripts run the following.
python3 examples/example01-python-binding.py
  1. Python Jupyter notebooks. To run the Jupyter notebook, one needs to have jupyter installed as a prerequisite. The run the Jupyter notebook, that creates an instance on your local server. Navigate to generated link to see the available Jupyter notebooks:
pip3 install jupyter
jupyter notebook

Using the library

The library can be used directly in the C/C++ code. The result of compilation is a static or dynamic library, that can be linked to ones project. Note, that the library is dependent on several other 3rd party libraries (e.g., libre2 or libsimlib), which are included in the repository.

First import the library in your code. If the library is properly installed, you can use the standard include.

#include <mata/nfa/nfa.hh>
nfa.hh
Nondeterministic Finite Automata including structures, transitions and algorithms.

We recommend to use the mata::nfa namespace for easier usage:

using namespace mata::nfa;
mata::nfa
Definition algorithms.hh:27

Start by creating an automaton with fixed number of states.

int main() {
Nfa aut(4);
mata::nfa::Nfa
A class representing an NFA.
Definition nfa.hh:114

You can set the initial and final states directly using the initializers.

aut.initial = {0, 1};
aut.final = {2, 3};

Further, you can add transitions in form of tripple (state_from, symbol, targets):

aut.delta.add(0, 0, 2);
aut.delta.add(1, 1, 3);

You can verify the state of your automaton by generating the automaton in .dot format.

aut.print_to_dot(std::cout);
return 0;
}

We recommend cmake for building projects using Mata. Provided the Mata is installed in the system directories, the CMakeLists.txt file for the example may look like:

cmake_minimum_required (VERSION 3.23.0)
project (my-project)
set (CMAKE_CXX_STANDARD 20)
# Find an installed Mata, or, if Mata is not installed, fetch the latest version, build it, and make it available in {#find-an-installed-mata-or-if-mata-is-not-installed-fetch-the-latest-version-build-it-and-make-it-available-in}
# your project. {#your-project}
include(FetchContent)
find_package(mata QUIET)
if(NOT mata_FOUND)
FetchContent_Declare(
mata
GIT_REPOSITORY https://github.com/VeriFIT/mata
GIT_TAG devel # Branch name, commit hash or a tag.
GIT_SUBMODULES "" # Explicitly disables submodule initialization/update.
GIT_SUBMODULES_RECURSE OFF # Ensures submodules are not downloaded recursively.
)
FetchContent_MakeAvailable(mata)
endif()
add_executable(my-project
my-project-source.cc)
target_link_libraries(my-project PUBLIC mata::libmata)

Using the Python binding

The python binding is installed (by default) to your local python package repository. You can either use the binding in your own scripts or in the python interpreter.

You can start using the binding by importing the libmata package.

import libmata.nfa.nfa as mata_nfa

In your own scripts, we recommend to use the standard guard for running the scripts, as follows.

if __name__ == "__main__":

The usage of the binding copies (to certain levels) the usage of the C++ library.

aut = mata_nfa.Nfa(4)
aut.initial_states = {0, 1}
aut.final_states = {2, 3}
aut.add_transition(0, 0, 2)
aut.add_transition(1, 1, 3)
print(aut.to_dot_str())

You can either run your scripts directly using python or compile it using the cython project.

Using the Rust binding

The API documentation of the Rust binding is on docs.rs. Its usage follows the C++ library:

use mata::{Error, Nfa, State, Symbol};
fn main() -> Result<(), Error> {
let mut aut = Nfa::with_states(4);
aut.add_initial(State::new(0))?;
aut.add_initial(State::new(1))?;
aut.add_final(State::new(2))?;
aut.add_final(State::new(3))?;
aut.add_transition(State::new(0), Symbol::new(0), State::new(2))?;
aut.add_transition(State::new(1), Symbol::new(1), State::new(3))?;
println!("{}", aut.dot());
Ok(())
}

Supported Automata Models

While we try to keep the provided library interface stable, Mata is still a project in its infancy. Hence, the interface is subject to change. For further information, see section Versioning.

Mata currently supports (non-)deterministic finite automata (NFAs), defined in include/mata/nfa/.

Warning
Mata provides an experimental (unstable) support for (non-)deterministic finite transducers (NFTs), defined in include/mata/nft/. The provided interface may change.

Versioning

Mata follows the versioning scheme GENERATION.MAJOR.MINOR, e.g. 1.2.3 where 1 is the generation number, and 2 the major version, and 3 the minor version. The MAJOR and MINOR versions follow loosely the Semantic Versioning scheme.

  • The GENERATION number represents our subjective generation of the Mata library. Typically, we increment the GENERATION number when a substantial change to the library is introduced, such as adding support for new automata models, extensive rewrite of (a part of) the Mata library, or to denote a new scientific paper documenting the latest developments in the Mata library is published, etc.
  • Generally, the changes in the MINOR version should not break the existing interface, but exceptions might occur.
  • The changes in the MAJOR version might introduce breaking changes that modify the existing interface and might require changing the code in your projects that use the Mata library.

Mata publishes releases from the master branch, and sometimes development releases from the devel branch.
