template<typename ...Ts>
using PostChain = typename internal::Chain<Ts...>::type

Build a post chain from its keys, outermost first, ending in the target set.

PostChain<Symbol, StateSet> is Post<PostEntry<Symbol, StateSet>>, which is mata::Post; PostChain<Symbol, Symbol, StateSet> is the arity-2 chain over the same key type.

A position may be either a key type or a mata::posts::ReservedKeysLike descriptor, so a post with a non-default reserved tail needs no change of spelling and no hand-written stack: 

using Narrow = PostChain<ReservedKeys<Symbol, 100>, StateSet>;  // one key, epsilon at 100

Template Parameters:

Ts – The key of each post from the outside in, then the innermost post. At least two, so a chain always has a key and always ends in a set of targets.

template<typename P, typename Fn>
void visit_targets(const P &post, Fn &&fn)

Apply fn to every target under post, at any nesting depth.

.

Note

if constexpr on key_arity turns the recursion into nested loops (same as a caller would write by hand), making this depth-generic visit free: measured at 0.99-1.01x of hand-written loops at every arity from 1 to 9. Fn is a template parameter and never a std::function: routing the same visit through one would cost 1.08x to 2.18x.

Parameters:

  • post – The post to visit. mata::arity_of is used to recurse down to the innermost post.

  • fn – The callable to apply to each target. It must accept a single argument of type target_of

The generic transition relation: a vector of posts indexed by source state.

A vector of posts indexed by source state, over a chain of posts ending in a set of targets. The depth is deduced from P as key_arity. Posts are named by key index, not by container count: Key<0> is the topmost symbol, and PostAt<key_arity> is the innermost post.

Keys on the transitions

Which outermost keys are in use. They ask nothing of a key beyond the ordering the posts already rely on, so a relation keyed by an interval or a weight has them too; what those keys stand for is that relation’s business. Protected for the same reason: a relation re-exports the ones it wants under the names that fit its keys, with a using-declaration or a forwarder. mata::Delta does the latter, as symbols, since for the shipped relation a key is one.

The three variants indexed by the key’s value need an unsigned integer for it.

PostType &mutable_state_post(State source)

Get mutable (non-constant) reference to the state post of source.

The function allows modifying the state post. BEWARE, IT HAS A SIDE EFFECT. If we try to access a state post of a source which is present in the automaton as an initial/final state, yet does not have allocated space in the relation, a new state post for source will be allocated along with all state posts for all previous states. This in turn may cause that the entire post data structure is re-allocated. Iterators into the relation will get invalidated. The relation cannot see edits made through the reference, so the next query of the transition count recounts. The reference may be used for edits only until that query: num_of_transitions(), empty(), or any operation that may call them. Obtain the reference again after such a query.

Parameters:

source – Source state of a state post to access.

Returns:

State post of source.

template<typename P>
struct SymbolTransitionTraits
#include <transition.hh>

Traits for a transition type: how to build one and how to take it apart.

A traits names a Type and builds transition with make(source, keys..., target), one key per post. The type itself owes a static parts(), which is what lets the hash, the formatter and the transition-shaped members of DeltaBase work without knowing the type.

Two are shipped. SymbolTransitionTraits yields the {source, symbol, target} triple and is the default at arity 1. KeyedTransitionTraits yields {source, keys, target} with the keys as a tuple and is the default above arity 1. DefaultTransitionTraits picks between them.

A module that wants its own field names writes a traits and passes it as the second argument of DeltaBase. Nothing is specialised, so two modules over the same chain can name their fields differently without touching each other: 

struct Transition {
State source{}; Symbol input{}, output{}; State target{};
bool operator==(const Transition&) const = default;
static auto parts(const Transition& t) noexcept {
using utils::ArgOf;
return std::tuple<ArgOf<State>, ArgOf<Symbol>, ArgOf<Symbol>, ArgOf<State>>{
            t.source, t.input, t.output, t.target};
    }
};
struct TransitionTraits {
using Type = Transition;
static Type make(State s, Symbol in, Symbol out, State t) { return {s, in, out, t}; }
};
// Right after the type, before anything hashes or formats one:
template <> struct std::hash<Transition> {
size_t operator()(const Transition& t) const noexcept { return mata::posts::hash_of(t); }
};
template <> struct std::formatter<Transition> { ... return mata::posts::format_parts(ctx.out(), t); ... };
