#define MATA_GENERATOR_COROUTINE_BEGIN

MATA_HAS_GENERATOR_SUPPORT (from the generated mata/config.hh) is 1 when std::generator (C++23 <generator>, P2502) was available to the standard library libmata was built with, 0 otherwise. Some standard libraries – notably Apple's system libc++ shipped with Xcode on macOS – do not implement it at all, regardless of -std=c++23, so code that depends on it must be guarded by this macro instead of assuming C++23 support implies it. The value is pinned at build time because the layout of the exported mata::utils::LazyGenerator depends on it; a consumer whose standard library disagrees is rejected here instead of silently compiling a different layout.

Brackets for definitions of coroutines returning std::generator. GCC's -Wmismatched-new-delete (part of -Wall) fires on every such coroutine built against libstdc++: the promise type allocates its frame with the plain ::operator new but deallocates through its own sized operator delete, which forwards to ::operator delete(ptr, size) via a deallocator function pointer stored in the frame. The pairing is correct, the compiler just cannot follow it. Known false positive, GCC PR middle-end/109224, which also fires inside libstdc++'s own test suite.
